# Audyt interfejsów użytkownika — Bioresonance

**Data:** 2026-11-07  
**Gałąź:** `main`  
**Zakres:** TUI, Desktop GUI, WebUI, Android GUI oraz ich wspólne kontrakty komunikacyjne.  
**Metoda:** statyczny przegląd kodu i konfiguracji repozytorium. Nie wykonano w tej zmianie kompilacji, testów CI ani testów z urządzeniem fizycznym.

## Werdykt

Repozytorium zawiera cztery rodziny interfejsów, ale nie jest jeszcze spójnym, kompletnym systemem wieloplatformowym. Najważniejsze ograniczenie ma charakter funkcjonalny i bezpieczeństwa: obecny firmware nie zapewnia potwierdzonego, działającego toru TCP/ENC28J60, a aktualne klienty protokołu v1 są diagnostyczne i tylko do odczytu.

**Status wydania: NOT READY.** Nie włączać sterowania wyjściami ani nie traktować aplikacji jako zwalidowanego wyrobu medycznego.

## 1. TUI

### Aktualna ścieżka
- `bash_tui/resonet_tui.py`
- `bash_tui/bioresonance_tui.sh`
- `bash_tui/test_resonet_tui.py`

Python TUI jest preferowanym punktem rozwoju: korzysta z binarnego ResoNet Protocol v1, walidacji ramek i diagnostycznego modelu komunikacji. Należy utrzymać go jako jedyny oficjalny TUI do czasu zakończenia porządkowania.

### Legacy
- `tui/bioresonance_tui.cpp`
- `tui/bioresonance_tui`
- `tui/TUI_README.md`

Starszy klient C++ zawiera tekstowe komendy i ścieżki wysyłania pakietów terapii, które są niezgodne z aktualnym, diagnostycznym kontraktem v1. Stara dokumentacja opisuje funkcje sterujące jako dostępne. Nie należy uruchamiać ani dystrybuować tej wersji. Pliki wymagają oznaczenia jako legacy/archiwalne, a usunięcie binarium powinno być osobną, świadomą zmianą po sprawdzeniu historii i zależności.

## 2. Desktop GUI

Preferowana implementacja: Qt 6 w `gui/qt/main.cpp`, budowana przez CMake i workflow Desktop GUI.

Zalety: natywna aplikacja, wykresy, prezentacja danych, eksport CSV, podział na obszary funkcjonalne i istniejące testy komunikacji/protokołu.

Braki:
- źródło LIVE_DEVICE nie jest jeszcze rzeczywistym, kompletnym połączeniem z urządzeniem;
- część obszarów (trening/gry) ma charakter demonstracyjny;
- historia i dane próbek wymagają trwałego magazynu;
- równoległe, starsze źródła w `gui/src/` wymagają jednoznacznego oznaczenia lub usunięcia po analizie zależności.

Qt 6 powinien pozostać główną platformą Desktop. Integracja urządzenia ma pozostać diagnostyczna, dopóki firmware i transport nie zostaną zweryfikowane.

## 3. WebUI

Główne pliki:
- `webui/index.html`
- `webui/diagnostics.html`
- `webui/diagnostics.php`
- `webui/api.php`
- `webui/tests/test_api_contract.py`

Obecna warstwa diagnostyczna ma istotne zabezpieczenia: API legacy zwraca HTTP 410, operacje mutujące są ograniczane tokenem, a klient powinien pozostać w trybie diagnostycznym. Dalszy rozwój powinien objąć trwałą historię, wielourządzeniowość, role, raporty, wykresy i testy PHP/JS.

Ograniczenie adresów do prywatnych zakresów IPv4 nie zastępuje listy dozwolonych urządzeń ani kontroli dostępu do panelu. Nie umieszczać sekretów w kodzie przeglądarki.

## 4. Android GUI

Główne pliki:
- `android_app/app/src/main/java/com/resonet/nano/MainActivity.kt`
- `MainViewModel.kt`
- `ArduinoCommunication.kt`
- `ResoNetProtocolV1.kt`
- `AndroidManifest.xml`

Mocne strony: Kotlin, MVVM, StateFlow, coroutines, walidacja HELLO i ramek, testy klienta TCP.

Problemy:
- widoczne akcje START/STOP/konfiguracji/skanowania nie są obsługiwane przez diagnostyczny transport v1;
- część metod zwraca UnsupportedOperationException;
- baza częstotliwości zawiera przykładowe rekordy zamiast gwarantowanego źródła produkcyjnego;
- trzeba ujednolicić stany połączenia i wyraźnie oddzielić dane symulowane od rzeczywistych;
- manifest wymaga ponownej oceny polityki cleartext i kopii zapasowych.

Nie wolno prezentować nieobsługiwanych operacji jako dostępnych ani oznaczać ich powodzenia bez potwierdzenia protokołu.

## 5. Wspólne problemy architektoniczne

1. Brak jednego formalnego źródła prawdy dla modeli i stanów UI.
2. Powielone parsery protokołu w C++, Pythonie, PHP i Kotlinie.
3. Niewystarczające wspólne wektory zgodności.
4. Nierównomierne pokrycie CI dla TUI, WebUI i firmware.
5. Rozbieżność pomiędzy częścią dokumentacji a rzeczywistymi możliwościami transportu.
6. Brak potwierdzonej integracji end-to-end z fizycznym urządzeniem.

Docelowo zachować natywne technologie platform, ale współdzielić formalną specyfikację protokołu, słownik błędów, model stanów, przykładowe ramki i testy zgodności.

## 7. Plan realizacji

### Etap A — ograniczenie ryzyka i dokumentacja
1. Oznaczyć C++ TUI jako legacy.
2. Usunąć sprzeczne instrukcje uruchamiania i deklaracje sterowania.
3. Oznaczyć Desktop i Android jako diagnostyczne.
4. Zachować wszystkie blokady operacji wyjściowych.

### Etap B — kontrakt wspólny
1. Utrwalić specyfikację ResoNet Protocol v1.
2. Dodać wspólne wektory ramek i przypadki błędów.
3. Ujednolicić stany: DISCONNECTED, CONNECTING, CONNECTED/DIAGNOSTIC, BUSY, FAULT, SAFE_LOCKOUT.
4. Wymagać ACK/odpowiedzi przed raportowaniem sukcesu.

### Etap C — platformy
1. Qt 6: rozdzielić widoki, model i transport; dodać trwałą historię.
2. Android: usunąć nieaktywne akcje z UI i używać rzeczywistego zasobu częstotliwości.
3. WebUI: rozbudować diagnostykę, role, historię i raporty.
4. Python TUI: utrzymać lekki klient diagnostyczny.

### Etap D — jakość
1. CI dla Python TUI i testów PHP.
2. Testy kontraktowe protokołu na wszystkich platformach.
3. Build firmware z przypiętym toolchainem.
4. Testy parserów, timeoutów, zerwania łącza i błędów ramek.
5. Testy HIL wyłącznie na stanowisku pomiarowym, bez człowieka.

## 8. Kryteria akceptacji

- Żaden interfejs nie sugeruje, że niezaimplementowana operacja się powiodła.
- Każda platforma rozróżnia dane rzeczywiste, symulowane i nieznane.
- Wszystkie klienty przechodzą wspólne testy ramek i błędów.
- Firmware potwierdza rzeczywisty stan łącza, a nie stan stubu.
- Utrata łączności prowadzi do zdefiniowanego bezpiecznego stanu.
- Dokumentacja odzwierciedla aktualny kod.
- Nie ma deklaracji gotowości medycznej bez odrębnej walidacji i oceny zgodności.

## 9. Dziennik realizacji — aktualizacja 2026-11-07

Poniższe zmiany wykonano bezpośrednio na gałęzi `main`, w oddzielnych commitach. Audyt nadal ma charakter statyczny; testy CI nie zastępują prób z fizycznym urządzeniem.

### Wdrożone korekty

- C++ TUI zostało oznaczone jako legacy; usunięto śledzone binarium, a dokumentacja wskazuje diagnostyczny klient Python jako aktualną ścieżkę TUI.
- Android: akcje START/STOP, skanowanie, przełączanie kanałów oraz zdalne logi, których transport v1 nie obsługuje, są wyłączone i opisane jako niedostępne.
- Android: ograniczono uprawnienia sieciowe i lokalizacyjne, wyłączono kopie zapasowe aplikacji oraz cleartext traffic w manifeście.
- WebUI: testy kontraktu dostosowano do aktualnego mostu diagnostycznego; uwzględniają odrzucanie starego API, token, HTTPS, ramki, CRC, zakres adresów i brak funkcji sterujących.
- CI: dodano testy WebUI do kontroli protokołu oraz zależności Qt/OpenGL do kompilacji.
- Desktop Qt 6: poprawiono błąd kompilacji związany ze zmianą przestrzeni nazw Qt Charts i konwersją rozmiaru kontenera.
- Test protokołu C++: usunięto operacje uboczne z makra `assert()`; sprawdzenia działają również w konfiguracji Release z `NDEBUG`.
- Klient sieciowy Desktop: odbiór danych oczekuje na gotowość gniazda w krótkich, maksymalnie 50-milisekundowych odcinkach, dzięki czemu może reagować na rozłączenie także na platformach, na których `shutdown()` nie wybudza niezawodnie `select()`.

### Wyniki weryfikacji

- `protocol-host`: PASS — kompilacja kodeka, testy protokołu, test klienta sieciowego, testy Python TUI i kontraktu WebUI.
- `php-lint`: PASS.
- `desktop-build`: PASS — konfiguracja, kompilacja Qt 6 i testy hosta zakończone powodzeniem w workflow uruchomionym dla commita `dd5088c0cb5881aabef40740efc52742f0407479`.
- Android: budowanie APK i testy jednostkowe zakończyły się powodzeniem w poprzednim przebiegu dla commita `c05731921c86083ab6005c58e7faf03b59ce2f62`; kod Androida nie był później zmieniany.
- Windows Qt 6: kompilacja zakończyła się powodzeniem w poprzednim przebiegu, ale test sieciowy wykazał opóźnienie rozłączenia. Poprawka mechanizmu oczekiwania została wprowadzona później; wymaga ponownego potwierdzenia w przebiegu Windows na aktualnym SHA.
